# 충돌 해결 절차

## Step 1: 수집

`git status`로 unmerged 파일 목록 X 수집. 각 unmerged 파일을 Read로 읽는다. 파일 안에 `<<<<<<<`, `=======`, `>>>>>>>` 마커가 있다.

## Step 2: 분류 (자문하라)

충돌은 3종류다. 어느 것인지 먼저 판정하라.

**(가) 단순 충돌**: 두 분기가 같은 줄을 단지 다른 형식으로 표현 (공백 차이, import 순서, 같은 의미의 변수명 차이). 한쪽 채택해도 다른 쪽 의도가 보존됨.

**(나) 양립 가능한 의미적 충돌**: 두 분기가 같은 자리를 다르게 바꿨지만 **둘 다 살려야 완성품이 됨** (예: 분기 A가 함수 시그니처에 인자 추가, 분기 B가 같은 함수 본문 로직 변경 → 둘을 합쳐야 동작). 한쪽만 택하면 다른 쪽 작업이 사라져 완성품이 깨진다.

**(다) 양립 불가**: 두 분기가 **서로 배타적인 아키텍처 결정**을 내림 (예: 같은 레이어를 A는 SQL, B는 NoSQL로). 통합 코드로 둘 다 살릴 수 없다. 사람이 방향을 정해야 한다.

## Step 3-A: 단순 충돌이면

- Edit으로 충돌 마커 (`<<<<<<<` ~ `>>>>>>>`) **범위 안만** 정리. 그 외 행 손대지 마라
- 양쪽을 모두 살려야 하면 두 변경을 순서대로 배치, 한쪽만이면 한쪽 채택 + 다른 영역/마커 삭제
- `artifacts/.merge-decisions/decision-{NNN}.md` 작성

## Step 3-B: 양립 가능한 의미적 충돌이면 (통합 코드 작성)

- 두 분기 변경을 함께 동작하도록 접합. 편집 범위는 충돌난 그 파일 안 (마커 범위 넘어도 됨).
- 금지: 충돌 안 난 파일 수정 / 새 기능 추가 / qa-report 조작.
- **검증 필수**: Bash로 빌드·import·테스트 (`python -c "import x"`, `python test.py`, `npm test`). 깨지면 고치고, 못 풀면 3-C로 강등.
- decision에 접합 방식 + 검증 결과 기록.

## Step 3-C: 양립 불가면 (abort + escalate)

- `git merge --abort` → `decision-{NNN}.md`에 "양립 불가 + 양쪽 배타적 선택 인용" → 종료 (orchestrator가 사용자 게이트)
- **확신 없으면 무리한 접합 대신 3-C.**

## Step 4: 마무리

모든 충돌 파일 정리 후:
- (Step 3-B를 거쳤으면) 통합 검증이 통과했는지 마지막 재확인
- `git add` 각 충돌 파일
- `git commit -m "forge: finalizer-merge sprint-{N}-branch-{K} (resolved {len} conflicts)"`
- 다음 분기로 진행

## decision-NNN.md 양식 (의무)

매 충돌 해결마다 한 개. NNN은 0부터 자동 증분.

```markdown
# Decision NNN - sprint {N} merge conflict in `<파일>`

## 채택
- 분기 `branch-K`의 변경 채택.
- 이유: 한 줄

## 버린 안
- 분기 `branch-J`의 변경.
- 무엇이었는가: 한 줄
- 왜 안 맞는가: 한 줄

## 판정 종류
- [ ] (가) 단순 충돌 (공백/import/형식) → 한쪽 채택
- [ ] (나) 양립 가능한 의미적 충돌 → 통합 코드 작성 + 검증
- [ ] (다) 양립 불가 → abort + escalate

## 통합 검증 (나 인 경우만)
- 실행한 검증 명령 + 결과 한 줄 (예: `python -c "import app"` → OK)

## 사후 검토 포인트
- 한 줄
```

**(다) 양립 불가 체크면 너는 abort + escalate 했어야 한다.** 양립 불가 체크하면서 머지 진행한 것은 자기합리화 (self-rationalization). **(나) 통합 체크면 반드시 통합 검증 결과를 적어야 한다** (검증 없는 통합은 미검증 코드 무단 삽입).
