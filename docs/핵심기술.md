# THE FORGE 핵심 기술 문서

---

## 0. 이 문서의 대상과 읽는 순서

**대상 독자:** THE FORGE를 처음 접하는 개발자, 포트폴리오 리뷰어

**핵심 한 줄 요약:** `forge run "요청"` 한 번이면, 기획부터 구현, 평가까지 자동으로 돌아간다 -- API 비용 0원으로.

**문서 구성:**
- 각 섹션은 **Why(기존 한계)** → **How(구현 방식)** → **What(핵심 특성)** 구조를 따른다
- 섹션 순서는 실제 `forge run` 실행 흐름과 일치한다
- 섹션 9는 다른 프로젝트에서 THE FORGE를 도구로 사용할 때 필요한 실전 레퍼런스다

| 섹션 | 다루는 내용 | 핵심 질문 |
|------|-----------|----------|
| 1 | 전체 아키텍처 | 이 시스템은 뭐고 왜 만들었나? |
| 2 | 자동 스프린트 루프 | 어떻게 자동으로 돌아가나? |
| 3 | 4-에이전트 파이프라인 | 각 에이전트가 뭘 받고 뭘 내보내나? |
| 4 | artifacts/ 파일 통신 | 에이전트끼리 어떻게 소통하나? |
| 5 | 체크포인트 복구 | 중간에 죽으면 어떻게 되나? |
| 6 | 양방향 알림 (Telegram + Slack) | 밖에서 어떻게 제어하나? |
| 7 | 비용 투명성 + Langfuse v4 OTEL | 토큰을 얼마나 쓰고 있는지 어떻게 아나? |
| 8 | 프로젝트 부트스트래핑 + 전역 설정 | 새 프로젝트에 어떻게 적용하나? |

| 10 | Journal 에이전트 | 사람이 읽을 엔지니어링 저널은 어떻게 자동 생성되나? |
| 11 | 진단/유지보수 인프라 | 서브에이전트가 조용히 실패하면? scaffold가 갱신되면? |

## 1. 전체 아키텍처: Harness-over-Harness

### 선택 이유

| 기존 방식의 한계 | THE FORGE의 해법 |
|-----------------|-----------------|
| Claude API를 직접 호출하면 토큰당 과금 발생 | Claude Code CLI(Max 정액제)를 subprocess로 호출 -- **API 비용 0원** |
| 단일 세션에서 기획+구현+평가 → 자기 합리화(Self-Rationalization) 발생 | 3개의 독립 프로세스로 역할 격리 |
| bash 스크립트 기반 하네스는 Windows 미지원, 에러 처리 취약 | Python 패키지로 전환 -- 크로스 플랫폼, Pydantic 모델 기반 |
| 프로젝트마다 하네스 코드를 복사해야 함 | `uv tool install`로 1회 설치, N개 프로젝트에서 재사용 |

### 구현 방법

- **구현 파일:** `src/forge/orchestrator.py`, `src/forge/cli.py`
- **핵심 로직:**
  - `forge` CLI가 `subprocess.run(["claude", ...])` 으로 Claude Code CLI를 호출
  - Planner/Evaluator: `claude -p --agent {name}` (비대화형 subprocess)
  - Generator: `claude` (대화형, stdin/stdout 직접 연결)
  - Max 플랜의 쿼터 안에서 동작하므로 토큰 사용량과 무관하게 월정액
- **참고 문서:** [Claude Code CLI](https://docs.anthropic.com/en/docs/claude-code), [typer](https://typer.tiangolo.com/), [Pydantic Settings](https://docs.pydantic.dev/latest/concepts/pydantic_settings/)

### 핵심 아키텍처 다이어그램

### 핵심 특성

- THE FORGE는 **도구**다. 프로젝트 코드에 포함되지 않는다. ruff, pytest처럼 별도 설치하여 사용
- Windows / macOS / Linux 크로스 플랫폼 지원
- API 키 불필요 -- Max 플랜 구독만 있으면 동작
- `uv tool install .` 한 줄로 설치, 어디서든 `forge` 명령 사용 가능

## 2. 자동 스프린트 루프 (Automatic Sprint Loop)

### 선택 이유

| 기존 방식의 한계 | 해결 필요성 |
|-----------------|------------|
| 1 스프린트 실행 후 수동으로 `forge run` 재실행 필요 | 야간/장시간 작업 시 사람이 계속 붙어있어야 함 |
| FAIL 시 수동으로 재진입 명령 실행 | 자동 대처 + 원격 선택지 필요 |
| 무한 루프 시 토큰/시간 낭비 방지 수단 없음 | 안전장치(Safety Guard) 필수 |

### 구현 방법

- **구현 파일:** `src/forge/orchestrator.py` -- `run_cycle()` 함수
- **핵심 로직:**
  - `run_cycle()` 내부의 `while True` 루프가 스프린트를 반복 실행
  - 루프 1회 = Contract 생성 → Generator 실행 → Evaluator 평가 → 결과 판정
  - PASS 시: sprint-N-done.md로 아카이브 → `has_next_sprint` frontmatter 확인 → 다음 스프린트
  - FAIL 시: 체크포인트를 `CONTRACT_DONE`으로 자동 롤백 → 사용자에게 3가지 선택지 제공
- **참고 문서:** [Anthropic Engineering Blog](https://www.anthropic.com/engineering)

### 스프린트 루프 흐름도

```
forge run "요청"
    │
    v
[Phase 1: Planning] ──── 프로젝트당 1회만 실행
    │ Planner가 spec.md + specs/*.md 생성
    │ Telegram으로 승인 요청
    v
┌─────────────────── Sprint Loop (while True) ───────────────┐
│                                                             │
│  ┌─ 안전장치 체크 ────────────────────────────────────┐    │
│  │ - 연속 FAIL 3회 도달?                               │    │
│  │ - 누적 시간 > max_total_minutes (1440분)?           │    │
│  │ - 스프린트 수 > max_total_sprints (20)?             │    │
│  │ - /stop 시그널 수신?                                │    │
│  │   -> 하나라도 해당 시 자동 중단 + Telegram 알림      │    │
│  └─────────────────────────────────────────────────────┘    │
│       │                                                     │
│       v                                                     │
│  [Phase 2: Contract]                                        │
│       │ Planner(Mode C)가 sprint-contract.md 생성           │
│       │ YAML frontmatter: has_next_sprint, next_preview     │
│       v                                                     │
│  [Phase 3: Generator]                                       │
│       │ interactive 세션 -- 코드 구현                        │
│       │ progress-log.md 업데이트 후 세션 종료                │
│       v                                                     │
│  [Phase 4: Evaluator]                                       │
│       │ qa-report.md 생성 (PASS/FAIL + 4차원 점수)          │
│       v                                                     │
│  [Phase 5: 결과 판정]                                       │
│       │                                                     │
│       ├── PASS + has_next_sprint: true                      │
│       │    -> Telegram: 점수 + 다음 스프린트 미리보기        │
│       │    -> /resume 대기 -> 루프 계속                     │
│       │                                                     │
│       ├── PASS + has_next_sprint: false                     │
│       │    -> Telegram: 프로젝트 완료 알림                  │
│       │    -> 루프 종료                                     │
│       │                                                     │
│       └── FAIL                                              │
│            -> 체크포인트 CONTRACT_DONE으로 롤백              │
│            -> Telegram: 실패 요약 + 선택지                  │
│            -> /resume: Generator 재진입                     │
│            -> /eval: Evaluator만 재실행                     │
│            -> /stop: 루프 종료                              │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 핵심 특성

- `forge run` 한 번 실행으로 프로젝트 완료까지 자동 진행 (v2.3 기본 동작)
- 스프린트 경계에서만 Telegram 승인 대기 -- 외출 중에도 폰으로 제어
- `--single-sprint`: v2.2 호환 모드 (1 스프린트만 실행)
- `--max-sprints N`: 최대 N개 스프린트만 실행하는 안전장치
- `has_next_sprint` frontmatter로 프로젝트 완료를 자동 판단 (Planner가 마지막 스프린트에 `false` 설정)

## 3. 4-에이전트 파이프라인 (4-Agent Pipeline)

### 선택 이유

| 기존 방식의 한계 | 해결 필요성 |
|-----------------|------------|
| 단일 세션에서 기획+구현+평가 수행 시 **자기 합리화** 발생 | 프로세스 격리로 역할별 독립 판단 보장 |
| "이 정도면 괜찮겠지"가 구현 중에 떠오르면 평가에 영향 | Evaluator가 별도 프로세스에서 엄격 평가 |
| 컨텍스트 오염: 구현 세부사항이 기획 판단을 흐림 | 에이전트 간 통신은 오직 파일로만 수행 |
| artifacts/는 기계용 — 사람이 다시 읽을 지식 부재 | 4번째 에이전트 Journal이 사람용 저널을 별도 추출 |

### 구현 방법

- **구현 파일:**
  - [src/forge/agents/planner.py](../src/forge/agents/planner.py) -- Planner subprocess 래퍼 (Mode A/B/C/D)
  - [src/forge/agents/evaluator.py](../src/forge/agents/evaluator.py) -- Evaluator subprocess 래퍼
  - [src/forge/agents/journal.py](../src/forge/agents/journal.py) -- Journal subprocess 래퍼
  - [scaffold/CLAUDE.md](../scaffold/CLAUDE.md) -- Generator 규칙
  - [scaffold/agents/planner.md](../scaffold/agents/planner.md) -- Planner 규칙
  - [scaffold/agents/generator.md](../scaffold/agents/generator.md) -- Generator 서브에이전트 규칙
  - [scaffold/agents/evaluator.md](../scaffold/agents/evaluator.md) -- Evaluator 규칙
  - [scaffold/agents/journal.md](../scaffold/agents/journal.md) -- Journal 규칙
- **참고 문서:** [Claude Code Agents](https://docs.anthropic.com/en/docs/claude-code)

### 3.1 Planner (기획자)

**실행 방식:** `claude -p --agent planner --max-turns {N} --permission-mode bypassPermissions "{prompt}"`

**4가지 동작 모드:**

| 모드 | 트리거 조건 | 입력 | 출력 | max-turns |
|------|-----------|------|------|-----------|
| **A: 생성** | spec.md 없음 + 사용자 요청 | 사용자 요청, templates/*.md | spec.md, specs/*.md | planner_max_turns (15) |
| **B: 리뷰** | spec.md 존재 | spec.md, specs/*.md | plan-review.md (READY / NEEDS_REVISION) | planner_review_max_turns (10) |
| **C: Contract** | 오케스트레이터가 스프린트 시작 시 호출 | spec.md, specs/*, progress-log.md, sprint-*-done.md | sprint-contract.md (YAML frontmatter 포함) | contract_max_turns (12) |
| **D: Revise** | 사용자가 Slack `revise` 모달로 수정 지시 (.revise-signal) | 사용자 지시문, spec.md, plan-review.md | spec.md (직접 Edit 예외 허용) + plan-review.md 수정 이력 추가 | planner_review_max_turns (10) |

**Mode D의 특별 권한:** Planner는 통상 spec.md를 직접 수정할 수 없지만, Mode D에서만 예외적으로 `Edit` 도구가 허용된다. 사용자가 외출 중 Slack 버튼 → 모달로 자연어 수정 지시를 보내면, Planner가 그 지시만 spec.md에 국소 반영하고 plan-review.md 최상단에 "수정 이력" 섹션을 자동 추가한다. 구현: [src/forge/agents/planner.py:88-116](../src/forge/agents/planner.py#L88-L116).

**sprint-contract.md YAML frontmatter (v2.3 필수):**

```yaml
---
sprint_number: 3
has_next_sprint: true           # 이 스프린트 이후 더 할 게 있는가
estimated_remaining_sprints: 2  # 남은 예상 스프린트 수
next_sprint_preview: |          # 다음 스프린트 작업 예고
  news_analyst, tax_analyst 구현
  추가 4개 노드 병렬 통합
---
```

**절대 금지 사항:** 코드 작성 금지, spec.md 직접 수정 금지, 세부 구현(라이브러리 버전, 함수명) 지정 금지

### 3.2 Generator (구현자)

**실행 방식 (현재):** `claude -p --agent generator --max-turns {N} --permission-mode bypassPermissions "{initial_prompt}"` -- 자동 비대화형 실행. 오케스트레이터가 [orchestrator.py:548-572](../src/forge/orchestrator.py#L548-L572)에서 직접 호출하며, 초기 프롬프트로 "qa-report.md FAIL 항목부터 우선 수정 → sprint-contract.md 체크박스 순서대로 구현 → 기능 완성 시 커밋"을 강제한다.

**자동 강제되는 커밋 규칙 (initial_prompt 내장):**
- 한 줄 영어, prefix는 `feat:` / `fix:` / `refactor:` 세 가지만 (예: `feat: add watcher debounce`)
- `Co-Authored-By` 서명 금지

**세션 시작 절차 (CLAUDE.md에 의해 강제):**
1. `progress-log.md` 읽기 (가장 먼저 -- 이전 상태 파악)
2. `spec.md` 읽기 (전체 프로젝트 이해)
3. `specs/*.md` 중 현재 작업 관련만 읽기
4. `sprint-contract.md` 읽기 (이번 스프린트 범위)
5. `qa-report.md`가 있으면 읽고 FAIL 항목 먼저 수정
6. `git log --oneline -10` (최근 커밋 확인)

**작업 규칙:**
- 한 번에 하나의 기능만 구현
- sprint-contract.md에서 우선순위 높은 미완료 항목 선택
- 완료 시 해당 항목을 `[x]`로 체크
- 기능 하나 완성할 때마다 커밋 (`feat: [기능명]`)

**세션 종료 절차 (필수):**
1. 모든 변경사항 커밋
2. `progress-log.md` 맨 위에 세션 기록 추가
3. 앱을 작동하는 상태로 남기기

**파일 소유권 규칙:**

| 파일 | Generator 권한 |
|------|---------------|
| spec.md, plan-review.md, specs/* | 읽기 전용 |
| sprint-contract.md | 체크박스만 `[x]` 수정 |
| progress-log.md | 읽기/쓰기 (필수) |
| qa-report.md, harness-cost-log.txt | 읽기 전용 |
| decisions/*.md | 읽기/쓰기 |
| src/, tests/ | 전체 권한 |

**컨텍스트 소진 대응:** Generator가 max-turns 또는 max_generator_minutes 한도에 도달하면 자동 종료된다. 종료 직전에 반드시 progress-log.md 업데이트 + 커밋. progress-log.md + git history가 다음 세션의 인수인계 역할. 타임아웃 시 오케스트레이터가 `warning` 알림 자동 발송.

### 3.3 Evaluator (평가자)

**실행 방식:** `claude -p --agent evaluator --max-turns {N} "{prompt}"`

**평가 절차:**

| Step | 행동 | 상세 |
|------|------|------|
| 1 | 컨텍스트 수집 | spec.md, sprint-contract.md, specs/*, progress-log.md, 소스코드(Glob→Read) |
| 2 | 자동화 검증 | pytest, npm test, lint, 타입 체크, 서버 실행 시도 |
| 3 | 코드 리뷰 | sprint-contract.md 각 항목별 구현 여부, 명세 일치, 에러 핸들링, 엣지 케이스 |
| 4 | 채점 | 4차원 점수 (각 1-10점) |
| 5 | 보고서 | qa-report.md 생성 |

**4차원 채점 기준:**

| 기준 | FAIL 임계값 | 평가 대상 |
|------|------------|----------|
| 기능 완성도 | 7점 미만 | sprint-contract 항목별 구현 여부 |
| 코드 품질 | 7점 미만 | 네이밍, 구조, 에러 핸들링 |
| 테스트 커버리지 | 7점 미만 | 테스트 존재 여부 + 실행 결과 |
| 명세 충실도 | 7점 미만 | specs/*.md와의 일치도 |

**자기 합리화 방지 규칙:**
- "이 정도면 괜찮다" = 버그를 통과시키는 순간
- 파일명:라인 번호 없는 지적은 지적이 아니다
- 테스트를 실행할 수 있는데 안 한 채 PASS 금지
- 의심스러우면 FAIL이다

**Playwright E2E 자동 통합:** 프로젝트에 `playwright.config.{ts,js,mjs}`가 존재하면 자동으로 `npx playwright test`를 실행하고 결과를 qa-report.md에 첨부

## 5. 체크포인트 복구 시스템 (Checkpoint Recovery)

### 선택 이유

| 기존 방식의 한계 | 해결 필요성 |
|-----------------|------------|
| 장시간 자동 루프 중 터미널 크래시, OOM, 네트워크 끊김 발생 | 진행 상태 소실 방지 |
| 처음부터 다시 실행하면 이미 완료된 Phase 재실행으로 시간/토큰 낭비 | 정확한 중단 지점부터 재개 |
| bash의 `should_run_phase()` + `phase_order()` case 문이 복잡 | IntEnum 비교 한 줄로 단순화 |

### 구현 방법

- **구현 파일:** `src/forge/checkpoint.py` (전체 61줄)
- **핵심 로직:**
  - `Phase` IntEnum으로 9단계 정의
  - `should_run(target) = self.phase <= target` -- 한 줄 비교로 실행 여부 판단
  - 각 Phase 시작 직전에 `save()` → 크래시 시 해당 Phase부터 재개
  - FAIL 시 `phase`를 `CONTRACT_DONE`으로 자동 되돌림

### Phase 전이 다이어그램

```
NONE(0) ──> PLANNING(1) ──> PLANNING_DONE(2) ──> CONTRACT(3) ──> CONTRACT_DONE(4)
                                                                       │
                                          ┌────────────────────────────┘
                                          v
                                   GENERATING(5) ──> GENERATING_DONE(6)
                                                           │
                                          ┌────────────────┘
                                          v
                                   EVALUATING(7) ──> EVALUATING_DONE(8)
                                                           │
                                          ┌────────────────┘
                                          v
                                   PASS? ──┬── Yes + has_next ──> CONTRACT(3) (다음 스프린트)
                                           ├── Yes + 마지막 ──> 프로젝트 완료
                                           └── No (FAIL) ──> CONTRACT_DONE(4) (자동 롤백)
```

### 복구 시나리오별 동작

| 중단 시점 | 저장된 Phase | `forge run` 시 동작 |
|----------|-------------|-------------------|
| Planner 실행 중 | PLANNING(1) | Planner 재실행 |
| 사용자 검토 대기 중 | PLANNING_DONE(2) | Sprint Contract 생성부터 |
| Contract 생성 중 | CONTRACT(3) | Contract 재생성 |
| Generator 세션 중 | GENERATING(5) | Generator 재시작 (progress-log + git으로 복구) |
| Evaluator 실행 중 | EVALUATING(7) | Evaluator 재실행 |
| 결과 판정 대기 중 | EVALUATING_DONE(8) | 결과 판정만 수행 |

**`forge run --from PHASE` 명시적 오버라이드:**

```bash
forge run --from generating    # Generator부터 강제 시작
forge run --from evaluating    # Evaluator부터 강제 시작
forge run --from planning      # 처음부터 재시작
```

이 옵션은 체크포인트를 해당 Phase 직전으로 자동 되돌린 뒤 실행한다.

### .harness-checkpoint 파일 형식

```json
  "detail": "generator session running",

}
```

## 6. 양방향 알림 (Telegram + Slack 듀얼 백엔드)

### 선택 이유

| 기존 방식의 한계 | 해결 필요성 |
|-----------------|------------|
| 야간 자동 루프 중 승인/중단을 터미널에서만 가능 | 모바일에서 원격 제어 필수 |
| bash의 curl + jq로 Telegram API 호출은 jq 의존성 문제 | httpx로 의존성 최소화 |
| 단방향 알림만으로는 FAIL 대응 불가 | 양방향 통신: 알림 + 명령 수신 + 파일 업로드 |
| Telegram 한 가지뿐이면 팀 협업/채널 관리/스레드 어려움 | Slack Socket Mode 백엔드 추가 — 1 App에서 N개 프로젝트 동시 운영 |
| 외출 중 spec 수정 시 파일 첨부는 기술 장벽 큼 | Slack 버튼 → Modal로 자연어 수정 지시 → Planner Mode D 자동 트리거 |

### 구현 방법

- **구현 파일:**
  - [src/forge/notifier/base.py](../src/forge/notifier/base.py) — `NotifierAdapter` ABC (Telegram/Slack 공통 인터페이스)
  - [src/forge/notifier/__init__.py](../src/forge/notifier/__init__.py) — 백엔드 팩토리 (`get_notifier()`, `FORGE_NOTIFIER_BACKEND`로 분기)
  - [src/forge/notifier/telegram/notifier.py](../src/forge/notifier/telegram/notifier.py) — Telegram 송신
  - [src/forge/notifier/telegram/receiver.py](../src/forge/notifier/telegram/receiver.py) — Telegram long polling 수신

- **참고 문서:** [Telegram Bot API](https://core.telegram.org/bots/api), [Slack Socket Mode](https://api.slack.com/apis/socket-mode), [Slack Block Kit](https://api.slack.com/block-kit), [httpx](https://www.python-httpx.org/), [slack_sdk](https://slack.dev/python-slack-sdk/)

### 6.5 백엔드 설정 우선순위

`FORGE_NOTIFIER_BACKEND` 값에 따라 단일 백엔드만 활성. 토큰은 `~/.forge/config.env`에서 전역 공유 가능.

```
FORGE_NOTIFIER_BACKEND="slack"

  + FORGE_TELEGRAM_BOT_TOKEN, FORGE_TELEGRAM_CHAT_ID                   ← Telegram 활성화
```

## 7. 비용 투명성과 관측성 (Cost Transparency & Observability)

### 선택 이유

| 기존 방식의 한계 | 해결 필요성 |
|-----------------|------------|
| 자동 루프가 토큰을 얼마나 소모하는지 파악 불가 | 무한 루프 시 리소스 낭비 방지 |
| 스프린트별 ROI 판단 근거 없음 | 에이전트별 시간 + 토큰 추적 필요 |
| Max 플랜은 토큰 과금이 없지만, 시간은 유한 | 시간 기반 예산 관리 |

### 구현 방법

- **구현 파일:** `src/forge/cost_tracker.py`
- **핵심 로직:** `SprintTracer` 클래스가 context manager 패턴으로 각 에이전트 실행을 감싸서 시간과 토큰을 추적
- **참고 문서:** [Langfuse Python SDK](https://langfuse.com/docs/sdk/python)

### 7.1 이중 토큰 추출 메커니즘

두 가지 실행 방식에 따라 토큰 추출 경로가 다르다:

| 에이전트 | 실행 방식 | 토큰 추출 방법 |
|---------|----------|--------------|
| Planner, Evaluator | `claude -p` (subprocess) | stdout에서 정규식 파싱: `Tokens: input X / output Y / cache Z` |
| Generator | `claude` (interactive) | `~/.claude/projects/{project-id}/*.jsonl`에서 시간 범위 내 usage 필드 합산 |

**subprocess 토큰 추출 (stdout 파싱):**
```
claude -p --agent planner "..."  실행
  → stdout 마지막에: "Tokens: input 45,231 / output 12,456 / cache 2,100"
  → 정규식으로 파싱하여 숫자 추출
```

**interactive 토큰 추출 (JSONL 파싱):**
```
~/.claude/projects/{project-id}/*.jsonl 파일에 세션별 기록
  → 각 줄의 assistant 메시지에 usage 필드 포함:
    {"type":"assistant","usage":{"input_tokens":...,"output_tokens":...}}
  → 세션 시작~종료 시간 범위로 필터링하여 합산
```

### 7.3 Langfuse v4 OTEL 트레이싱 (구현 디테일)

`SprintTracer` ([cost_tracker.py](../src/forge/cost_tracker.py))는 Langfuse 4.x의 OpenTelemetry 기반 API를 사용한다. v3에서 v4로의 이행 포인트:

| 항목 | v3 (이전) | v4 (현재) |
|------|----------|----------|
| Trace 생성 | `langfuse.trace(...)` | `start_as_current_observation(as_type="span")` 컨텍스트 매니저 — 루트 span이 자동으로 trace를 만든다 |
| Trace 메타데이터 (이름/세션/유저) | `trace.update(...)` | `propagate_attributes(trace_name=..., session_id=..., user_id=...)` CM으로 root span 내부에서 전파 |
| 비용 자동 계산용 Span 타입 | `Generation` | `start_as_current_observation(as_type="generation")` — span 타입은 Usage/Cost 컬럼에 반영 안 됨 |
| Usage 필드 | `usage={...}` | `usage_details={"input": ..., "output": ..., "cache_read": ...}` |

**모델 자동 추론:** `_extract_tokens_from_jsonl()`이 `~/.claude/projects/<project-id>/*.jsonl`을 시간 범위 필터링으로 스캔할 때, 각 assistant 레코드의 `message.model` 필드도 함께 집계한다. 가장 많은 토큰을 쓴 모델을 대표 모델로 채택해 `lf_span.update(model=...)`로 전달 → Langfuse가 내장 pricing 테이블로 cost를 자동 산출.

**Plan B (stdout fallback):** JSONL에서 토큰을 못 찾으면 stdout의 `Tokens: input X / output Y / cache Z` 라인을 정규식 파싱.

### 7.4 Langfuse 듀얼레이어 트레이싱

THE FORGE는 두 개의 독립적인 Langfuse 추적 레이어를 운영한다:

```
┌─ Layer 1: 하네스 메타 추적 (forge가 관리) ──────────────┐
│                                                         │
│  .env의 FORGE_LANGFUSE_* 키로 설정                      │
│                                                         │
│  Sprint Trace (1 스프린트 = 1 Trace)                    │
│    ├── Planner Span    (4분, 45K tokens)                │
│    ├── Contract Span   (2분, 28K tokens)                │
│    ├── Generator Span  (127분, 1.1M tokens)             │
│    └── Evaluator Span  (8분, 67K tokens)                │
│                                                         │
│  → "이 프로젝트의 3번째 스프린트에 얼마나 걸렸나"        │
└─────────────────────────────────────────────────────────┘
        ↕ 완전 별개 — 서로 독립적으로 동작
┌─ Layer 2: 프로젝트 코드 내 추적 (Generator가 구현) ─────┐
│                                                         │
│  대상 프로젝트 자체의 Langfuse 키로 설정                 │
│  specs/langfuse-tracing.md에 따라 Generator가 코드에 삽입│
│                                                         │
│  → "프로젝트 코드가 LLM을 어떻게 사용하고 있나"         │
└─────────────────────────────────────────────────────────┘
```

**Layer 1은 선택적 의존성:** Langfuse 키가 설정되지 않아도 harness-cost-log.txt에는 항상 기록된다.

## 8. 프로젝트 부트스트래핑 (forge init Scaffold 시스템 + 전역 설정)

### 선택 이유

| 기존 방식의 한계 | 해결 필요성 |
|-----------------|------------|
| 매 프로젝트마다 CLAUDE.md, AGENT.md, templates 수동 작성 | 반복 작업 제거 |
| 프로젝트마다 harness/ 폴더 복사 (v1.x) | 도구로 1회 설치, scaffold는 초기화만 |
| Hooks 설정을 수동으로 해야 함 | settings.json 자동 머지 |
| 프로젝트마다 .env에 동일한 Slack/Langfuse 토큰 중복 입력 | `~/.forge/config.env` 전역 1회 입력 → 모든 프로젝트 자동 로드 |
| 같은 디렉토리명을 여러 위치에 두면 Slack 봇 식별 충돌 | `~/.forge/registry.json`으로 충돌 감지 + 대체 이름 제안 |
| 프로젝트명/봇 이름 수동 명명은 실수 유발 | 디렉토리명에서 snake_case + PascalCase 자동 추론 |
| MCP 서버 / 플러그인 설정 누락 가능 | `.mcp.json`도 scaffold에서 함께 복사 |

### 구현 방법

- **구현 파일:** `src/forge/cli.py` -- `init` 함수 및 헬퍼들
- **핵심 로직:**
  1. `_scaffold_dir()`: THE_FORGE 패키지 내 scaffold/ 디렉토리 탐색
  2. `_copy_scaffold()`: CLAUDE.md, AGENT.md, templates/ 복사
  3. `_merge_claude_settings()`: `.claude/settings.json` hooks 스마트 머지 (중복 방지)
  4. `_ensure_env_and_pyproject()`: `.env` 템플릿 + `pyproject.toml [tool.forge]` 섹션 추가
  5. `_ensure_gitignore()`: artifacts/ 경로들을 `.gitignore`에 추가

### forge init --force (업데이트 시)

THE_FORGE를 업데이트한 후 scaffold 변경사항을 기존 프로젝트에 전파할 때 사용:
- 기존 파일을 `artifacts/.backup/`에 타임스탬프 포함하여 백업
- scaffold 원본으로 덮어쓰기
- 사용자가 커스터마이징한 내용은 `.backup/`에서 복구 가능

### templates/ 선택적 참조 시스템

Planner가 템플릿을 읽는 효율적 3단계 프로세스:

| 단계 | 읽는 파일 | 소모 턴 | 목적 |
|------|----------|---------|------|
| 1 | `templates/INDEX.md` | 1턴 | 전체 템플릿 목차에서 후보 선정 |
| 2 | 후보 파일의 frontmatter | 0.5턴 | 키워드 매칭으로 정밀 필터링 |
| 3 | 최종 선택된 템플릿 본문 | 1턴 x N개 | 실제 내용 참고 |

불필요한 템플릿을 모두 읽는 것을 방지하여 토큰 효율성 확보.

### 설정 로드 우선순위

```
1. 환경변수 (최우선)               예: FORGE_TELEGRAM_BOT_TOKEN=...
2. 프로젝트 .env                   예: FORGE_PROJECT_NAME="my-bot"
3. ~/.forge/config.env (전역)      예: FORGE_SLACK_BOT_TOKEN="xoxb-..."
4. forge.toml [forge]              (v2.2 이전 레거시, 하위 호환)
5. pyproject.toml [tool.forge]    예: max_sprint_minutes = 180
6. autoinfer 자동 추론             project_name = 디렉토리명 → snake_case
7. 코드 기본값 (최하위)
```

**3-tier 분리 원칙:**

| 위치 | 용도 | git 커밋 | 예시 키 |
|------|------|---------|--------|
| `~/.forge/config.env` | 모든 프로젝트가 공유하는 토큰 (1회만 입력) | ❌ (홈 디렉토리, 권한 0o600) | `FORGE_SLACK_BOT_TOKEN`, `FORGE_LANGFUSE_*` |
| 프로젝트 `.env` | 이 프로젝트만의 식별값/오버라이드 | ❌ (`.gitignore`) | `FORGE_PROJECT_NAME`, `FORGE_TELEGRAM_CHAT_ID` |
| `pyproject.toml [tool.forge]` | 팀이 공유하는 동작 파라미터 | ✅ | `max_sprint_minutes`, `evaluator_max_turns` |

### 8.1 `forge setup` 전역 설정 마법사

`~/.forge/config.env`에 Slack/Langfuse 토큰을 한 번만 저장. 이후 모든 프로젝트의 `ForgeConfig`가 이 파일을 자동 로드. 구현: [src/forge/setup_wizard.py](../src/forge/setup_wizard.py).

```mermaid
flowchart TB
    START([forge setup]) --> EXIST{~/.forge/config.env<br/>존재?}
    EXIST -->|Yes| LOAD[현재 값 로드 + 마스킹 표시]
    EXIST -->|No| EMPTY[빈 dict로 시작]
    LOAD --> ASK
    EMPTY --> ASK
    ASK[대화형 prompt:<br/>NOTIFIER_BACKEND<br/>SLACK_BOT_TOKEN<br/>SLACK_APP_TOKEN<br/>SLACK_CHANNEL<br/>LANGFUSE_*]
    ASK -->|빈 엔터| KEEP[기존 값 유지]
    ASK -->|새 값| OVERWRITE[덮어쓰기]
    KEEP --> WRITE
    OVERWRITE --> WRITE
    WRITE[~/.forge/config.env 작성<br/>POSIX는 chmod 0o600]
    WRITE --> DONE([완료])
```

**마법사 특성:**
- 기존 토큰은 `xxxx…yyyy` 형식으로 마스킹 표시 (`_mask()` 함수)
- 빈 엔터 = 기존 값 유지 (덮어쓰지 않음)
- `--reset` 플래그로 처음부터 다시 입력
- 사용자가 직접 추가한 비공식 키도 보존됨

**Telegram 파일 전송 시 caption 규칙:**
- caption 없이 전송 → `artifacts/{파일명}`에 저장

- `/forge-status` slash command는 인자 없으면 모든 프로세스가 응답, 인자 있으면 일치 프로세스만 응답

| 현재 체크포인트 | `forge run` 실행 결과 |
|---------------|---------------------|

| PLANNING_DONE | Sprint Contract 생성부터 |

### 9.5 상황별 대처법

**QA FAIL 시:**

```
상황: Sprint N이 FAIL 판정을 받음
  │
  ├── Telegram 알림 수신 (qa-report.md 첨부)
  │     점수 + 실패 항목 + 선택지 표시
  │
  ├── 선택지 1: /resume
  │     → Generator가 재진입하여 FAIL 항목 수정
  │     → qa-report.md의 FAIL 항목을 먼저 읽고 수정 시작
  │
  ├── 선택지 2: /eval
  │     → AGENT.md(Evaluator 규칙)를 수정한 후 사용
  │     → 평가 기준 조정 후 동일 코드를 재평가만
  │     → 결과에 따라 다시 PASS/FAIL 판정
  │
  └── 선택지 3: /stop
        → 자동 루프 종료
        → 나중에 forge run으로 재개 가능 (체크포인트 보존)
```

**예기치 않은 크래시 시:**

```
상황: 터미널 종료, OOM, 네트워크 끊김 등
  │
  └── forge run  (그냥 다시 실행하면 됨)
        → .harness-checkpoint에서 중단 Phase 읽기
        → 해당 Phase부터 자동 재개
        → 이미 완료된 Phase는 건너뜀
```

**누적 예산 초과 시:**

```
상황: 누적 시간이 max_total_minutes(기본 1440분 = 24시간) 초과
  │
  ├── 자동 중단 + Telegram 알림 (cost-log.txt 첨부)
  │
  └── 대처 방법:
      ├── pyproject.toml의 max_total_minutes 값 증가
      └── forge run으로 재시작 (체크포인트에서 재개)
```

**NEEDS_REVISION (설계 수정 필요) 시:**

```
상황: Planner 리뷰가 NEEDS_REVISION 판정
  │
  ├── Telegram 알림 (plan-review.md 첨부)
  │
  ├── 선택지 1: spec.md 수정 후 /resume
  │     → Telegram으로 수정된 spec.md 파일 전송 (caption: artifacts/spec.md)
  │     → /resume 입력 → Planner가 재리뷰
  │
  └── 선택지 2: /skip
        → 리뷰 결과 무시하고 Sprint Contract 생성 진행
```

**연속 FAIL 3회 자동 중단 시:**

```
상황: 같은 스프린트에서 3회 연속 FAIL
  │
  ├── 자동 중단 + Telegram 알림
  │
  └── 대처 방법:
      ├── qa-report.md 확인 → 근본 원인 파악
      ├── AGENT.md(Evaluator) 수정 → 평가 기준 조정
      ├── 또는 직접 코드 수정 후 forge run --from evaluating
      └── 또는 pyproject.toml의 max_consecutive_fails 값 증가
```

## 10. Journal 에이전트 — 사람용 엔지니어링 저널 자동 생성

### 선택 이유

| 기존 방식의 한계 | 해결 필요성 |
|-----------------|------------|
| `artifacts/`는 에이전트 간 통신용 (기계 가독) — 시간 지나면 맥락 잃음 | 사람이 다시 읽을 수 있는 **에러/결정/팁** 저널 필요 |
| `progress-log.md`는 인수인계용 — 다음 세션 위주 | 프로젝트 전체 회고용 별도 문서 필요 |
| 스프린트 종료 시마다 직접 회고 작성은 부담 | 4번째 에이전트가 자동 추출 |
| 결정 근거를 잊으면 같은 실수 반복 | `decisions/` + git log + `qa-report.md`에서 근본 원인/교훈 자동 채굴 |

### 구현 방법

- **구현 파일:** [src/forge/agents/journal.py](../src/forge/agents/journal.py), [src/forge/cli.py:107-186](../src/forge/cli.py#L107-L186) (`journal` 명령), [scaffold/agents/journal.md](../scaffold/agents/journal.md) (에이전트 규칙)
- **실행 방식:** `claude -p --agent journal --max-turns {journal_max_turns}` 자동 비대화형
- **출력 위치:** `docs/journal.md` (artifacts/ 바깥 — 사람이 직접 읽고 git에 커밋하는 문서)

### 10.1 동작 모드 (3 가지 범위 지정)

| 모드 | 트리거 | 우선 자료 |
|------|--------|----------|
| **단일 스프린트** | `forge journal --sprint 3` | `sprint-3-done.md` + 관련 `decisions/`, `progress-log.md`, `qa-report.md` |
| **범위 (연속/불연속)** | `forge journal --sprints 1-4` 또는 `1,3,5` | 해당 sprint-*-done.md들 |
| **날짜 이후** | `forge journal --since 2026-04-01` | `git log --since=...` 커밋 + 그 기간 artifacts 변화 |
| **자동 (기본)** | `forge journal` | `docs/journal.md` 최상단 엔트리 날짜 이후 변경분 |

### 10.2 자료 추출 흐름

```mermaid
flowchart TB
    INVOKE([forge journal]) --> SCOPE{범위 지정?}
    SCOPE -->|--sprint N| S1[sprint-N-done.md]
    SCOPE -->|--sprints 1-4| S2[해당 sprint-*-done.md들]
    SCOPE -->|--since DATE| S3[git log --since + artifacts 변화]
    SCOPE -->|없음 자동| S4[journal.md 최상단 엔트리 이후 변경]

    S1 & S2 & S3 & S4 --> READ
    READ[Journal 에이전트가 Read]
    READ --> SRC1[decisions/decision-*.md]
    READ --> SRC2[progress-log.md 최신 섹션]
    READ --> SRC3[qa-report.md FAIL 항목]
    READ --> SRC4[harness-cost-log.txt ERROR 레코드]
    READ --> SRC5[git log fix:/refactor: 커밋 메시지]

    SRC1 & SRC2 & SRC3 & SRC4 & SRC5 --> EXTRACT[Errors & Root Causes / Decisions / Tips & Gotchas / Carry-overs / Performance Notes 5 카테고리로 정리]
    EXTRACT --> WRITE[docs/journal.md 최상단에 새 엔트리 PREPEND]
    WRITE --> NOTIFY[활성 백엔드에 최상단 엔트리 요약 + 파일 첨부]
```

### 10.3 엔트리 포맷 (엄수)

- **헤더:** `## YYYY-MM-DD — {project_name} — {범위}` (자동 모드에서는 범위 생략)
- **한 줄 요약:** 헤더 직후 빈 줄 다음 1~3 문장
- **5개 섹션:** Errors & Root Causes / Decisions / Tips & Gotchas / Carry-overs (있을 때만) / Performance Notes (이상치 있을 때만)
- **링크 규칙:** 모든 파일/함수 참조는 `[라벨](상대경로#Lline)` 마크다운 링크. 평문 금지.
- **커밋 참조:** 해시는 백틱 코드(`commit \`abc1234\``), 파일 링크와 em dash로 구분

### 10.4 중복 방지 + Slack/Telegram 자동 첨부

- 작성 전 `journal.md` 최상단 엔트리 날짜를 읽어 **겹치는 범위면 새 엔트리 추가 대신 기존 엔트리 업데이트**
- CLI가 작성 완료 후 [_extract_latest_journal_entry()](../src/forge/cli.py#L209-L231)로 최신 엔트리 발췌 → 활성 백엔드에 `journal` 이벤트로 전송 (파일 자체도 첨부)

## 11. 진단 / 유지보수 인프라

### 11.1 Subprocess 진단 로깅 (`_logging.report_subprocess`)

`claude -p --agent ...` 호출이 returncode=0으로 성공해도 **서브에이전트 매칭 실패 / 플러그인 미활성 / MCP 호출 실패**가 stderr에 묻혀 사라지는 문제가 있었다. [src/forge/_logging.py](../src/forge/_logging.py)가 이를 가시화한다.

| 패턴 감지 | 결과 출력 |
|----------|---------|
| `returncode != 0` | 빨간 실패 메시지 + stderr/stdout tail |
| stderr에 `unknown subagent` / `agent not found` / `plugin not enabled` / `MCP .* failed` | 노란 경고 + stderr tail |
| stderr에 `subagent` / `Task tool` / `plugin` / `marketplace` / `MCP server` 키워드 (성공이긴 해도) | dim 회색 안내 + stderr tail (주목용) |
| 그 외 | 조용히 패스 |

오케스트레이터의 모든 subprocess 호출이 이 함수를 거치므로, 조용히 실패하는 케이스가 없다.

### 11.2 Plugin 자동 활성화 (`feature-dev@claude-plugins-official`)

[scaffold/settings.json](../scaffold/settings.json)이 `enabledPlugins`에 `feature-dev@claude-plugins-official: true`를 포함하므로, `forge init`만 하면 Claude Code 공식 feature-dev 플러그인이 모든 에이전트 세션에서 사용 가능.

### 11.3 PostToolUse Hook — Edit/Write 후 자동 ruff

scaffold settings.json의 hook:

```json
"PostToolUse": [{
  "matcher": "Edit|Write",
  "hooks": [{
    "type": "command",
    "command": "if [ -f pyproject.toml ]; then ruff check --fix --quiet 2>/dev/null || true; fi",
    "timeout": 10
  }]
}]
```

→ Generator가 코드를 작성/수정한 직후 자동 린트. Python 프로젝트에서만 동작 (다른 언어는 no-op).

### 11.4 `forge update-templates` / `forge update-agents` — scaffold 재동기화

THE_FORGE를 업데이트한 뒤 기존 프로젝트들에도 scaffold 변경사항을 전파하기 위한 명령. `forge init --force`는 너무 무겁고(.env까지 백업), CLAUDE.md/templates/agents만 갱신하고 싶을 때 사용.

```mermaid
flowchart LR
    UP([forge update-templates]) --> SCAN[설치본 scaffold/templates/*.md 스캔]
    SCAN --> DIFF{프로젝트 templates/<br/>파일과 다름?}
    DIFF -->|동일| SKIP[건너뜀]
    DIFF -->|다름| BACKUP[기존을 .backup/에 백업]
    BACKUP --> COPY[새 버전 복사]
    DRYRUN{--dry-run?}
    SCAN --> DRYRUN
    DRYRUN -->|Yes| LIST[변경 대상만 출력 후 종료]
```

`forge update-agents`도 동일 패턴으로 `.claude/agents/*.md`를 갱신.

### 11.5 `forge notify` — Hooks/스크립트용 알림 유틸

```bash
forge notify session_stop "Generator 세션 정상 종료" /path/to/file
```

Stop hook이나 외부 스크립트에서 활성 백엔드로 일회성 알림 보낼 때 사용. 백엔드는 `~/.forge/config.env` + 프로젝트 `.env` 조합으로 자동 결정 — 별도 인자 불필요.

## 부록: 용어 사전

| 용어 | 설명 |
|------|------|
| **Harness** | AI 에이전트를 오케스트레이션하는 제어 시스템. THE FORGE는 Claude Code CLI 위에 동작하는 "harness-over-harness" |
| **Sprint** | 하나의 작업 사이클. Contract 생성 → Generator 구현 → Evaluator 평가까지가 1 스프린트 |
| **Phase** | 오케스트레이터의 실행 단계. NONE(0)부터 EVALUATING_DONE(8)까지 9단계 |
| **Checkpoint** | `.harness-checkpoint` 파일에 저장되는 현재 Phase. 크래시 시 복구에 사용 |
| **artifacts/** | 에이전트 간 통신에 사용되는 모든 파일이 저장되는 디렉토리 |
| **Signal File** | Telegram Receiver와 Orchestrator 사이의 통신용 빈 파일 (`.approval-signal` 등) |
| **Sprint Contract** | 이번 스프린트에서 구현할 항목 목록. YAML frontmatter에 `has_next_sprint` 포함 |
| **progress-log.md** | Generator가 세션마다 작성하는 작업 기록. "미래의 자신에게 보내는 편지" |
| **scaffold/** | `forge init` 시 프로젝트에 복사되는 템플릿 원본 디렉토리 |
| **CLAUDE.md** | Generator(메인 세션)의 행동 규칙 파일. Claude Code가 자동 로드 |
| **AGENT.md** | 서브에이전트(Planner, Evaluator, Journal)의 행동 규칙 파일 |
| **SprintTracer** | 스프린트 단위로 시간과 토큰을 추적하는 context manager |
| **Max 플랜** | Anthropic의 Claude 정액제 구독. API 과금 없이 CLI 사용 가능 |
| **NotifierAdapter** | Telegram/Slack 공통 ABC. `enabled`/`notify`/`start`/`stop` 4개 메서드만 노출 |
| **Mode D (Revise)** | Planner가 사용자 자연어 지시로 spec.md를 직접 Edit하는 예외 모드. Slack 모달이 트리거 |
| **`~/.forge/config.env`** | 모든 프로젝트가 공유하는 전역 토큰 파일. `forge setup`이 생성/갱신 |
| **`~/.forge/registry.json`** | 디렉토리명 충돌 감지용 프로젝트 레지스트리 — `forge init` 시 갱신 |
| **autoinfer** | 디렉토리명에서 `project_name` (snake_case) + `bot_display_name` (Forge-PascalCase) 자동 추론 |
| **Journal** | 4번째 에이전트. `docs/journal.md`에 사람이 읽는 엔지니어링 저널을 추출 |
| **Block Kit** | Slack 메시지의 풍부한 UI 빌딩 블록 (header / section / actions / input). buttons는 actions로, 모달은 input으로 매핑 |
| **Socket Mode** | Slack의 WebSocket 기반 이벤트 수신 방식. 외부 endpoint 불필요. 1 App에서 N개 동시 연결 |
